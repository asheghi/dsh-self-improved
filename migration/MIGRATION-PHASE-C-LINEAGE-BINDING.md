# Phase C stable historical lineage binding — identity only, not fork admission

## Scope

Added `verifyContinuityHistoricalLineageBindingV02` beside the existing standalone native ancestry verifier in [src/continuity-ancestry-v02.ts](../src/continuity-ancestry-v02.ts). Both paths now share one private complete-observation/ancestry validator and lease owner. The existing `verifyContinuityAncestryV02` public DTO and full-current-source `proofHash` semantics remain unchanged.

The new detached, body-free binding uses **format 2 / source bindingVersion 3**. It includes the project, selected child's normalized immutable-header hash, inherited floor, selected historical cut and digest through that cut; an ordered child→parent edge per ancestor with both normalized header hashes, identities, inherited floors and the copied parent-prefix digest; and a root-termination identity. Each edge is recomputed from native observations and checks the exact inherited prefix before producing hashes. Child events after the selected cut and parent events outside the copied prefix do not affect the historical binding, while a changed selected child cut or copied prefix does. The empty inherited prefix is represented by cut `-1` and the digest of the canonical empty list.

The ancestry verifier in this document remains a fresh native identity derivation; by itself it does not authenticate caller-supplied bindings, attest human intent, or grant permission. Later isolated v3 envelope/capture/work modules now persist and recompare lineage anchors through claim, handoff, and a cold preview prototype. Those compositions remain unregistered and are not wired into Host startup, UI, Remote, Continue, or main-plugin dispatch. The shared Phase A/B `isDelegatedHeader` behavior is unchanged; ordinary forks remain denied by current action paths.

## Limits and next gates

The isolated v3 envelope's historical lineage binding is now recomputed identically after native JSONL cold restore in a distinct OS process, and a separate `ContinuityCaptureV03` fixture persists/reopens its checkpoint, pending job, and consumed human boundary in a second file-backed v3 store; see the [native-source restart fixture](MIGRATION-PHASE-C-HOST-RESTART.md). Across the two child processes, a separate v3 fixture completes one job with a fixed synthetic note and reopens its handoff; revoked policy then makes both current handoff readers deny it, including after re-enable. The verify child also claims a second reopened job, revalidates its lease against cold native source, then revokes/re-enables policy and confirms the job stays cancelled, the lease fails, and stale boundary capture is refused; no provider is invoked. This remains low-level owner coverage with synthetic boundary/note input and does not authenticate Host provenance or wire v3 into normal runtime admission. Independent source review found no material blocker; that review was source-only and did not rerun tests. Complete ancestor reads and hashing remain O(full history); this is not a global memory bound or a cryptographic golden root. Concurrent native reads are not one cross-store snapshot. Parent-tail stability proves identity equivalence at the copied cuts, not ancestry authenticity against rewritten logs.

Before any fork admission, follow [the integration gate](MIGRATION-PHASE-C-FORK-INTEGRATION.md): the versioned projection/source/job binding and lineage comparisons through claim, settlement, handoff, and a default-deny preview prototype now exist only as isolated code. Still required are the authenticated Host/UI provenance and intent path, target/ancestor default-deny policy materialization, integration into an accepted runtime, v3 provider execution, authenticated runtime settlement/handoff and cancellation/revocation integration, full main-plugin/Host restart, and browser gates. Phase C remains open; this work does not change Phase A/B acceptance or authorize live-profile/data changes.
