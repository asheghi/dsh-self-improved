## Minimal unavoidable runtime change

Restore the API cookie check in the installed Connection owner, preserving the Host/Origin fence:

`requestRejection(request)` must return `403` when Host/Origin is rejected, otherwise `this.browserAuth.isAuthenticated(request) ? undefined : 401` instead of unconditional success. Remove/disable the `DSH_DISABLE_LOCAL_AUTH` index bypass for the acceptance host. This restores authenticated HTTP admission but is **not alone** a durable prompt/Continue receipt or proof of a physical human click.

For the v3 exact-message provenance gate, the core authenticated prompt route must additionally expose a supported Host-owned admission receipt/event bound to the actual Host-generated message ID and session ID, after Agent/attachment validation and for the exact successful admission only. It must carry non-client-forgeable authenticated request provenance, distinguish new admission from deduplicated acknowledgment, and define rejection/append ordering so failed delivery cannot become authority. The plugin can resolve its own project/generation, pair the receipt to the exact live append using the existing ledger, and revoke/burn on cancellation, disposal, policy change, and replay. A request ID or shared Peer ID alone is insufficient. Continue should consume a Host-verifiable, short-lived one-shot intent bound to authenticated caller, target, selected job/source identity, policy epoch and cancellation; an in-process `invoke({peer: connection.operator})` must not mint it.

Run acceptance on an auth-enabled, unpatched isolated Host: no-cookie, forged/expired/wrong-authority cookie, client-forged receipt, in-process peer spoof, duplicate/mismatched/inherited append, replay/relay/cross-offer, cancellation/revocation, restart, and genuine authenticated positive cases. Existing fixtures and this audit do not supply those results. Runtime/profile changes require separate authorization and are outside this workspace-only task.

## Concrete incremental core receipt contract

This cannot honestly be a Connection-only fix: [Gateway preparation](</home/bahman/github/dsh-v0.2/node_modules/@deepseek-ai/dsh-api-gateway/lib/index.js#L953-L985>) currently defaults even direct in-process invocation to `request.peer ?? this.operatorPeer()`. Implement the following distinct increment across Connection, Gateway and Session controller (and publish the matching generated/type contracts), not a plugin-created attestation:

1. In Connection, maintain an owner-private WeakMap/WeakSet admission authority. Only the HTTP route after successful signed-cookie verification may mint an opaque request capability containing a random request nonce, exact authority/operator, and carrier signal. Associate it with the bridged Request in a private map and remove/revoke it when the carrier settles or cancels. Do not expose a public receipt-mint operation, signing secret, capability constructors, or a way for `invoke({peer})` to create it.
2. Extend the Connection RPC handler's internal carrier context to forward this opaque capability, and expose an exact verifier/claim operation that checks membership, signal, lifetime, endpoint and single-use status. Both unary and stream admission must use the same authority; absent context remains valid for ordinary automation but has no authenticated-operator status. Exact fetch/internal paths do not inherit authority by receiving the shared operator.
3. At Gateway `invokeRpc` / `prepareInvocation`, retain the verified carrier context on `GatewayInvocation` as read-only authenticated admission. Never derive it from `request.peer`, the operator fallback, request JSON, request ID, or caller-supplied flags. Direct public `invoke` and local transports have no capability. A plugin checking Continue must claim an endpoint/argument-bound one-shot intent and recheck signal/lifetime rather than merely reading Peer ID.
4. In Session controller prompt, use the invocation capability only after resolving the exact Agent, validating attachments and creating the actual Host message. Expose an awaited Host-only admitted-prompt hook bound to actual message ID/session/request nonce, before delivery can append; issue provisionally, finalize on successful delivery, revoke on delivery failure/cancel. This ordering must be reviewed against synchronous `steer`/`followup` append behavior. Deduplicated acknowledgments issue no new receipt. The plugin adds current project/policy-generation binding and uses its existing one-use exact live-append ledger; provisional evidence cannot authorize capture/provider work before finalization.
5. Verify direct `typertGateway.invoke` with omitted or supplied OperatorPeer remains unauthenticated; authenticated successful new prompt pairs exactly once; inherited append, mismatched IDs/nonce, receipt replay, delivery rejection, cancellation, policy ABA and restarted Host capabilities fail closed. Only then integrate the plugin callback and run mounted auth-enabled acceptance.

A subsequent concrete workspace candidate now implements a **unary-only** core increment and conservative v2 main-plugin admission. It is not applied or fully accepted; see below. Neither cookie restoration alone nor partial candidate verification closes the full Host/Continue acceptance gate.
